# Граница работ backend / ML

## Восстановление локальной ML-сборки и исправления пользователя

До восстановления из нового пользовательского Excel после получения кода 84710fc оставался старый `classifier.joblib`;
`action_states_v8.joblib/json`, `data/raw/team_annotations.json` и
`data/annotations/actions_objects_v2.json` не переданы. README нового релиза не доказывает наличие этих артефактов.
Теперь отдельно обучен `recovery_review_v1`: 24 development-видео по новой таблице,
исходные 8 test-видео не используются для fitting. Неполные и неоднозначные метки не превращаются в норму.
Готовые веса v8 и его разметка не восстановлены и не выдаются за эту новую модель.
Команда `python -m scripts.audit_active_model` создаёт локальный отчёт с активным артефактом,
списком недостающих файлов и анализом сохранённых validation-оценок. Никакого обучения,
изменения threshold или обращения к test этот аудит не выполняет.

У старого baseline на сохранённой validation все четыре отрицательных ролика отмечены как
положительные. Ни один порог не уменьшает число этих ложных тревог без пропусков положительных.
Это историческая оценка на использовавшихся для выбора порога данных, не новый независимый тест.
Правильность исходных меток требует согласования: релиз описывает исправления X-12/X-24 и других
роликов, которых нет в локальном Excel/manifest. Не переносить эти изменения автоматически из прозы.

В UI под новым результатом есть форма «Исправить результат / отметить пропущенное действие».
Она сохраняет только текстовую запись и SHA-256 видео в папку `feedback` рядом с SQLite.
Видео/кадры туда не копируются. Запись содержит источник данных, интервал, наблюдаемое действие,
тип исправления и идентификатор модели. Можно выбрать сценарий из `research/rules.json`:
условия, исключения и требуемая последовательность кадров показываются до сохранения.
Выбор человека записывается как `human_selected_research_candidate`, а не как ответ модели.
В R01 найдено внутреннее противоречие между требованием незавершённого обслуживания и
исключением «Операция не завершена»; UI предупреждает о необходимости согласовать формулировку.

Все исправления имеют `pending_review` и `eligible_for_training=false`. Ложная тревога
в интервале не превращается в отрицательную метку всей записи. Для отметки всей записи
требуется подтверждение полного просмотра. После дататона удалять эти записи вместе с
другими данными проекта; кнопка удаления результата не удаляет отдельные исправления.

Порядок следующего обучения: получить доверенную сборку и исправленную разметку;
согласовать неоднозначные метки; связать интервалы с наблюдаемыми действиями и условиями research;
сохранить группы похожих видео и не переносить test в train; обучить отдельный кандидат;
выбирать параметры на train/validation и сравнить ложные тревоги, пропуски, типы и локализацию.
Тестовые видео жюри и записи с неизвестным происхождением исключаются.
Простое повышение порога, подстановка текста нормы или объединение всех видео в train
не считается улучшением модели. Новую модель подключать только после документированной проверки.

Код `ml/`, weights, classifier и обучающая разметка не меняются доработками сервиса. ML-разработчик владеет точностью, типами, локализацией, наблюдаемыми описаниями, sampling/threshold и validation. Backend владеет доставкой, deadline, схемой, JPEG-валидацией, хранением и представлением.

## Совместимый результат

### Воспроизведение восстановления из пользовательского Excel

Локальные входы: исходный Excel `fortevis_*.xlsx` в корне, неизменённый
`artifacts/manifest.json`, `data/raw/recovery_type_map.json`, видео из manifest и ResNet18.
Карта типов хранится вне Git вместе с разметкой. Она сохраняет семантические решения,
неоднозначные строки и пользовательское уточнение X-4: около 57 с. X-4 и X-47 — точные
дубликаты; в новом обучении это один пример. Имя/хеш видео не используются для выбора
ответа при inference. Веса нового классификатора сохраняются отдельно от старого.

```powershell
$workbookPath = (Get-ChildItem -File fortevis_*.xlsx).FullName
python -m ml.recovery_training --workbook $workbookPath --mapping data/raw/recovery_type_map.json
python -m scripts.refit_recovery_release --workbook $workbookPath --mapping data/raw/recovery_type_map.json
python -m ml.recovery_training --workbook $workbookPath --mapping data/raw/recovery_type_map.json --model models/recovery_review_v1.joblib --evaluate-test
python -m scripts.evaluate_recovery_groups --workbook $workbookPath --mapping data/raw/recovery_type_map.json --model models/recovery_review_v1.joblib
```

Команды fitting отказываются перезаписывать существующие модели. Для нового эксперимента
задавайте новые `--model` и `--output-dir`/`--directory`; refit принимает предыдущую модель
через `--source`. Не используйте эти команды для автоматического переобучения после каждой загрузки.
После просмотра test-результатов дальнейший подбор по этим видео уже не является независимой проверкой.

Первый fit: 19 train-видео, полный кадр ResNet18, сравнение appearance/sequence и трёх
фиксированных порогов на 7 validation-видео с известной бинарной меткой. Выбран appearance,
порог 0.55. Финальный refit использует 24 типизированных development-видео, включая прежнюю
validation-часть; её метрики нельзя приписывать финальной модели. Порог перенесён без новой
калибровки. X-17 исключён из fitting из-за родственного X-16 в test. Неизвестные метки и типы
не заменяются отрицательными. Для слабых положительных без времени выбираются окна по
multiple-instance learning; это не равнозначно ручной интервальной разметке.

8 исходных test-видео остаются вне fitting. Результат финальной модели: TP=1, FP=2, TN=2,
FN=3; правильно названных положительных видео 0/4. Трёхчастная групповая диагностика на
development с сохранением известных пар: TP=3, FP=6, TN=6, FN=9, правильных типов 0/12.
На X-4, включённом в train, основной тип prior_deposit_outside_storage выделен на 58.03 с;
есть также неопределённый кандидат на 54.03 с. Если исключить X-4 из fitting в групповой
диагностике, событие пропускается. Это прямое ограничение обобщения, а не доказательство
успешного распознавания действия по новым видео.

Локальные отчёты лежат в `artifacts/recovery_20261018/`: annotation_audit.json,
selection.json, release_refit_plan.json, release_x4_regression.json,
recovery_review_v1_test_evaluation.json и recovery_review_v1_grouped_diagnostic.json.
Исходные файлы, признаки, отчёты с деталями видео и модели не публикуются в Git.
Для отката задайте в `.env` `FORTEVISION_MODEL=models/classifier.joblib` и соответствующий
`FORTEVISION_CONTAINER_MODEL`, затем перезапустите сервис. Старые веса не менялись.

Следующие полезные данные: точные интервалы наблюдаемых действий в разрешённых development-видео;
уточнения пустых/неоднозначных строк X-1, X-10, X-29–X-32, X-34; новые независимые положительные
и похожие нормальные примеры каждого сценария, включая другой ракурс. Для документа/ключа
нужны крупные видимые объекты и размеченные рамки, для R02 — последовательность двух клиентов
и судьба предыдущей партии денег. Видео жюри не включать в обучение.

Точка интеграции остаётся `python -m ml.predict --video PATH --model PATH --weights PATH --device cpu --budget SECONDS --output PATH`. Никаких сетевых скачиваний при inference. Ненулевой exit code → failed. API ограничивает процесс оставшимся общим временем. Поддерживайте числовой float-бюджет, включая значения меньше секунды.

JSON должен содержать `verdict` и `violations`. Каждое событие: type, timecode_sec, description, evidence_frames. `image_base64` должен декодироваться в настоящий JPEG, 1–3 кадра, не более 4096 px на сторону. Общий output ограничен 16 MiB. Лишние обязательные поля не вводить. API добавляет job_id/status и измеренное время. Не возвращайте job_id/status из ML CLI.

Для обученных типов добавьте необязательный стабильный `event_type` (например, ID категории из согласованной taxonomy). `type` — человекочитаемое имя. `description` — только действительно наблюдаемое действие и ограничения вывода; нельзя превращать общий score в выдуманный сюжет. Не переносите описание research в prediction без детектора соответствующего действия.

## Проверенные нормативные ссылки

Backend не сопоставляет бинарный score с нормой. Адаптер `app/rule_links.py` принимает event_type только для конкретного типа (не общей категории), ищет записи в `configs/rules.json` и проверяет:

1. Поля источника, пункта, проверяющего и даты, требуемые RuleEngine.
2. `detector_model_sha256` точно совпадает с текущим classifier.joblib.
3. `validation_report` указывает на существующий локальный отчёт (относительный путь считается от configs).
4. Ссылка использует HTTPS и официальный домен adilet.zan.kz / old.adilet.zan.kz / nationalbank.kz / www.nationalbank.kz.

Полная запись содержит `event_type`, `source_title`, `source_url`, `section`, `verified_by`, `verified_at`, `detector_model_sha256`, `validation_report`. Отчёт должен включать сопоставление наблюдаемых условий/исключений с классом и результаты проверки. Существование файла и хеш — технический допуск; они не заменяют содержательную экспертизу и не доказывают юридическую корректность.

При совпадении backend добавляет optional `rule_references` и источник в description; UI показывает документ, пункт и ссылку. Переданные самим ML rule_references не считаются автоматически проверенными и удаляются до этого сопоставления. Пустой каталог остаётся допустимым технически, но требование ТЗ о нормативе для события остаётся незакрытым до подтверждения типов и правил.

Не копируйте весь research/rules.json в configs: это разные схемы и разные статусы готовности. Привязки для текущего бинарного baseline намеренно отсутствуют. После замены модели старые привязки перестают применяться, пока не проверен новый хеш.

## Передача нового релиза

Передайте комплект модели + metadata + weights, перечень типов, новые честные метрики, утверждённые привязки и лицензионные сведения. Заменять комплект следует при остановленном сервисе; UI/API затем перезапустить. Не менять JSON-хеш вручную для обхода проверки. Backend не запускает train и не подбирает threshold.
